# リスクと対策

確認日: 2026-10-20

## 位置づけ

リスクの種類は Claude Code などのエージェント全般と同じで、新しいものではない。ブラウザ拡張機能で変わるのは次の3点。

1. 影響範囲: ログイン済みのブラウザ全体に権限が届きうる
2. 信頼の境界: ブラウザ側とローカル環境側をまたぐ
3. 記録: シェルの履歴のような形で残りにくい

「拡張機能は危ない」ではなく、「既存のエージェントのリスクを、ブラウザという広い場所に置いたもの」と捉える。

## 想定リスク

| # | リスク | 内容 |
|---|---|---|
| 1 | プロンプトインジェクション | ページの文章に引きずられる。上層の汚染が下層への依頼として流れる |
| 2 | ログイン済みセッション | 同じブラウザの他のサービスにも理屈上は届く |
| 3 | ページへのコード送信 | そのページの Cookie や API を使える。ComfyUI ではノード導入・実行の API も呼べる |
| 4 | 供給網とネットワーク | カスタムノードは任意コードの実行。外部公開していると外から触られる |
| 5 | 承認の形骸化 | 便利になるほど「全部許可」に寄る |
| 6 | 情報の外部流出 | 画面の内容はモデルに送られる。パスやユーザー名が映ることがある |
| 7 | 公開時の混入 | 自分のパスやトークンがリポジトリに入る。スキルが他人の環境で強い権限を持つ指示になる |
| 8 | 規約・制限 | 自動操作で利用を制限される可能性 |

## 実際に起きたこと: ページへのコード送信(リスク 3)

最初の運用では、上層の Claude がページ内で JavaScript を実行し、ComfyUI の API を直接呼んでいた([記録](log/2026-10-20.md)の「自動試行の仕組み」)。

- 便利な面: 画面のワークフローを変えずに、値を変えた試行を何十回も回せる。
- 見えにくい面: 何が送られたかは画面に出ない。入力フォルダへのファイルのアップロード(上書きを含む)も、この経路で行われていた。
- 同じ経路で、ノードの導入や削除の API も理屈の上では呼べる。それを止める技術的な仕組みはない。
- 今回の運用では、上層の作業記録によると、ComfyUI の作業中のページ移動は 0 回、Web 検索も 0 回だった。ノードの導入・削除もしていない。外部の文章が入る入口は、実際にはなかった(上層の Claude が自分の作業記録を確認して報告したもの)。

## 中継を通らない経路

人間の中継が押さえるのは、上層から下層への「依頼文」だけ。上層が書いたものを下層が後から読むと、人間を通らずに情報が流れる。今回の運用では次の 3 つがあった。

- 上層が ComfyUI の入力フォルダに保存・上書きしたファイル
- 上層が書いた引き継ぎメモ(Claude Docs)
- 上層が編集・書き出したワークフローの JSON

ここに外部の文章が混ざっていたら、中継をすり抜ける。下層は、上層が作ったファイルの中身も鵜呑みにせず、データとして扱う。

(この節は、上層の Claude 自身がこのリポジトリを読んで指摘した内容をもとにしている)

便利さとリスクは、同じ仕組みの裏表になっている。

## 入口になる場面

外部ページを読まなければリスクは下がる。ただし実運用では、足りないノードの調査(GitHub、Hugging Face、Civitai)や他人のワークフローの読み込みで外部の文章が入ってくる。ここが入口になる。

「ComfyUI だけ触る」は技術的な制限ではなく、お願いベースであることに注意する。

## ブラウザの分離は各自で判断する

ComfyUI は起動時に既定のブラウザで開くため、何もしなければ普段使いの Chrome(ログイン済みのサービスがある状態)で作業が始まる。このリポジトリの最初の実行もその状態だった。

ComfyUI の試行錯誤では、AI に再試行と確認を自動で続けさせることになり、人間が一つひとつ確認しない時間ができる。「AI が何をするかわからない」ことを前提にすると、ログイン済みのブラウザを明け渡すのは避けたい。

ただし、影響の大きさは人によって違う(Google をほとんど使っていない、もともとログインしていない、など)。ここでは選択肢を示し、どれを選ぶかは各自に任せる。

| 選択肢 | 分離の度合い | 備考 |
|---|---|---|
| 普段使いのプロファイル | なし | 手軽。ログイン済みのサービスすべてが届く範囲に入る |
| 作業専用のプロファイル | 中〜高 | Google と同期しない。拡張機能のサイトアクセスを ComfyUI に限定する |
| シークレットウィンドウ | 高 | 終了時に Cookie が消える。拡張機能はシークレットでの実行を許可する設定が必要(要確認) |

## 対策

| 対策 | 対応するリスク |
|---|---|
| 上層と下層を直接つながず、人間が中継する | 1 |
| 外部情報を読む場面・導入の場面は人間が承認する | 1, 4 |
| 下層は上層からの依頼も、上層が作ったファイルの中身も鵜呑みにしない | 1 |
| 作業専用の Chrome プロファイル、またはシークレットウィンドウを使い、Google アカウントと連携しない(下記) | 2, 6 |
| 拡張機能のサイトアクセスを ComfyUI のアドレスに限定、操作タブは1つ | 2, 3 |
| 上層の作業に要らないコネクタはすべてオフにする(メール、カレンダー、ドキュメントへの書き込み、共有される記憶など) | 2, 6 |
| カスタムノードは [approval.md](approval.md) の手順で導入する | 4 |
| 専用の Python 環境(venv)で動かす | 4 |
| ComfyUI をローカル以外に公開しない | 4 |
| 承認ポイントを固定し、数を絞る | 5 |
| 画面に映るパス・ユーザー名・他のタブに注意する | 6 |
| 公開前にパスとトークンの混入を確認する | 7 |
| ペースを落とし、確認画面や制限が出たら止めて人間に返す。検出を回避する手順は書かない | 8 |
